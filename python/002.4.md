# Python Topic 2.4 — Decorators

## 1. What is a Decorator?

A **decorator** is a callable that takes another function/callable, adds or modifies its behavior, and returns a callable.

Example:

```python
def decorator(func):

    def wrapper():
        print("Before")
        func()
        print("After")

    return wrapper
```

Usage:

```python
def greet():
    print("Hello")

greet = decorator(greet)

greet()
```

Output:

```text
Before
Hello
After
```

Mental model:

```text
Original function
       ↓
   decorator
       ↓
   wrapper
       ↓
Modified behavior
```

---

# 2. `@decorator` Syntax

Python provides syntactic sugar for applying decorators.

```python
@decorator
def greet():
    print("Hello")
```

is approximately equivalent to:

```python
def greet():
    print("Hello")

greet = decorator(greet)
```

Therefore, `decorator` is **not a Python keyword**.

The `@` is decorator syntax, while `decorator` is simply a conventional name for a function/callable that performs the decoration.

---

# 3. Decoration Time vs Runtime

This distinction is important.

Consider:

```python
@decorator
def greet():
    print("Hello")
```

When Python executes the function definition:

```text
Decoration time
      ↓
decorator(greet)
      ↓
wrapper created
      ↓
greet now points to wrapper
```

Later, when:

```python
greet()
```

is called:

```text
Runtime
   ↓
wrapper executes
   ↓
original greet executes
```

Therefore:

> Decorators are applied when the function definition is executed; the resulting wrapper executes later when the decorated function is called.

---

# 4. Why Use a Wrapper?

A wrapper allows us to add behavior before and/or after the original function.

```python
def decorator(func):

    def wrapper():
        print("Before")

        func()

        print("After")

    return wrapper
```

The original function remains focused on its actual work.

The wrapper handles additional behavior.

---

# 5. Decorators and Higher-Order Functions

A decorator is closely related to higher-order functions.

A higher-order function is a function that:

* accepts another function as an argument, or
* returns a function.

A decorator does both:

```python
def decorator(func):
    ...
    return wrapper
```

It:

1. Receives `func`.
2. Creates/returns another function `wrapper`.

Therefore:

```text
Higher-order function
        ↓
    Decorator
```

---

# 6. Decorators and Closures

Decorators commonly use closures.

Example:

```python
def decorator(func):

    def wrapper():
        print("Before")
        func()
        print("After")

    return wrapper
```

`wrapper()` references `func`.

But `func` belongs to the enclosing `decorator()` scope.

Therefore `wrapper` closes over `func`.

Conceptually:

```text
wrapper
   ↓
closure
   ↓
func → original function
```

So a typical decorator combines:

```text
Higher-order function
        +
Nested function
        +
Closure
        =
Decorator
```

---

# 7. Decorators with Function Arguments

A decorator should generally support arbitrary function arguments using:

```python
*args
**kwargs
```

Example:

```python
def decorator(func):

    def wrapper(*args, **kwargs):
        print("Before")

        result = func(*args, **kwargs)

        print("After")

        return result

    return wrapper
```

Now it can decorate functions with different signatures:

```python
@decorator
def add(a, b):
    return a + b
```

Calling:

```python
add(10, 20)
```

results in:

```text
wrapper(10, 20)
      ↓
func(10, 20)
      ↓
30
```

`*args` captures positional arguments.

`**kwargs` captures keyword arguments.

---

# 8. Why `*args` and `**kwargs`?

A generic decorator shouldn't need to know the signature of every function it decorates.

For example:

```python
@decorator
def f(a, b):
    ...


@decorator
def g(name, age, city):
    ...


@decorator
def h(x, y=10, *, debug=False):
    ...
```

A generic wrapper can handle all of them:

```python
def wrapper(*args, **kwargs):
    return func(*args, **kwargs)
```

---

# 9. Preserve the Return Value

A common decorator mistake is:

```python
def decorator(func):

    def wrapper(*args, **kwargs):
        print("Before")
        func(*args, **kwargs)
        print("After")

    return wrapper
```

Suppose:

```python
@decorator
def add(a, b):
    return a + b
```

Then:

```python
result = add(2, 3)
```

will make:

```python
result == None
```

because `wrapper()` doesn't return the original result.

Correct:

```python
def decorator(func):

    def wrapper(*args, **kwargs):
        print("Before")

        result = func(*args, **kwargs)

        print("After")

        return result

    return wrapper
```

Now:

```python
result = add(2, 3)
```

gives:

```python
result == 5
```

---

# 10. `functools.wraps`

Decorators can hide metadata of the original function.

Example:

```python
def decorator(func):

    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)

    return wrapper
```

After decorating:

```python
@decorator
def greet():
    """Say hello."""
    print("Hello")
```

The decorated function may now have:

```python
greet.__name__ == "wrapper"
```

instead of:

```python
greet.__name__ == "greet"
```

The docstring and other metadata can also be lost.

Use:

```python
from functools import wraps


def decorator(func):

    @wraps(func)
    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)

    return wrapper
```

`@wraps(func)` preserves important metadata of the original function.

### Production rule

For a normal Python decorator:

```python
@wraps(func)
```

should generally be used on the wrapper.

---

# 11. Decorator with Its Own Arguments

There are two different types of arguments to understand.

### Function arguments

```python
@decorator
def add(a, b):
    ...
```

Here:

```text
a, b → arguments of add()
```

### Decorator arguments

```python
@retry(max_attempts=3)
def call_api():
    ...
```

Here:

```text
max_attempts=3 → argument of retry decorator
```

These require an additional function level.

Example:

```python
def retry(max_attempts):

    def decorator(func):

        def wrapper(*args, **kwargs):

            for attempt in range(max_attempts):
                try:
                    return func(*args, **kwargs)
                except Exception:
                    print("Attempt failed")

        return wrapper

    return decorator
```

Usage:

```python
@retry(max_attempts=3)
def call_api():
    ...
```

---

# 12. Why Are Three Function Levels Required?

Consider:

```python
@retry(3)
def call_api():
    ...
```

This is approximately:

```python
call_api = retry(3)(call_api)
```

First:

```python
retry(3)
```

must return something callable.

That returned callable then receives:

```python
call_api
```

So:

```text
retry(3)
   ↓
returns decorator
   ↓
decorator(call_api)
   ↓
returns wrapper
   ↓
call_api points to wrapper
```

The wrapper can retain both:

```text
max_attempts = 3
func = original call_api
```

through closures.

---

# 13. Can We Use `decorator(func, 3)`?

Yes, but not directly with normal `@decorator` syntax.

This is valid:

```python
def decorator(func, number):
    ...
    return wrapper


greet = decorator(greet, 3)
```

But:

```python
@decorator
def greet():
    ...
```

is approximately:

```python
greet = decorator(greet)
```

It doesn't automatically supply another argument.

For:

```python
@decorator(3)
def greet():
    ...
```

Python effectively does:

```python
greet = decorator(3)(greet)
```

Therefore `decorator(3)` must return another callable.

---

# 14. Multiple Decorators

Consider:

```python
@decorator1
@decorator2
def greet():
    print("Hello")
```

This is equivalent to:

```python
greet = decorator1(decorator2(greet))
```

The **bottom decorator is applied first**.

Conceptually:

```text
Original greet
     ↓
decorator2
     ↓
decorator1
     ↓
final greet
```

---

# 15. Runtime Execution of Multiple Decorators

Suppose:

```python
def A(func):

    def wrapper():
        print("A Before")
        func()
        print("A After")

    return wrapper


def B(func):

    def wrapper():
        print("B Before")
        func()
        print("B After")

    return wrapper
```

And:

```python
@A
@B
def f():
    print("F")
```

Equivalent:

```python
f = A(B(f))
```

Final structure:

```text
f
↓
A wrapper
↓
B wrapper
↓
original f
```

Calling:

```python
f()
```

produces:

```text
A Before
B Before
F
B After
A After
```

---

# 16. Application Order vs Execution Order

For:

```python
@A
@B
def f():
    ...
```

### Decoration/application order

```text
B → A
```

because:

```python
f = A(B(f))
```

### Runtime execution order

```text
A → B → original → B → A
```

Assuming both decorators have before/after logic.

### Easy interview rule

> **Bottom decorator is applied first; top decorator executes first.**

---

# 17. Why Does the Outer Decorator Execute First?

After decoration:

```text
f
↓
A wrapper
↓
B wrapper
↓
original f
```

Calling:

```python
f()
```

first enters A's wrapper.

A then calls its captured `func`, which is B's wrapper.

B then calls its captured `func`, which is the original function.

Therefore:

```text
A wrapper
   ↓
B wrapper
   ↓
original
```

---

# 18. Multiple Decorators and Closures

Each wrapper can close over the function it receives.

For:

```python
@A
@B
def f():
    ...
```

conceptually:

```text
A wrapper
   ↓
closure
   ↓
func → B wrapper
              ↓
            closure
              ↓
            func → original f
```

So multiple decorators form a chain of wrapper functions and closures.

---

# 19. Decorator Order Can Change Behavior

Decorator order can affect correctness.

For example:

```python
@cache
@authenticate
def get_data():
    ...
```

means:

```python
get_data = cache(authenticate(get_data))
```

While:

```python
@authenticate
@cache
def get_data():
    ...
```

means:

```python
get_data = authenticate(cache(get_data))
```

These are not necessarily equivalent.

Decorator order can affect:

* Authentication
* Caching
* Logging
* Retry behavior
* Performance
* Error handling
* Security

Therefore decorator ordering can be a real production concern.

---

# 20. Class-Based Decorators

A decorator does **not have to be a function**.

It can be a **callable object**.

A class instance becomes callable when its class implements:

```python
__call__()
```

Example:

```python
class Logger:

    def __init__(self, func):
        self.func = func

    def __call__(self, *args, **kwargs):
        print("Before")

        result = self.func(*args, **kwargs)

        print("After")

        return result
```

Usage:

```python
@Logger
def greet(name):
    print(f"Hello {name}")
```

This:

```python
@Logger
def greet(name):
    ...
```

is approximately:

```python
greet = Logger(greet)
```

`Logger(greet)` creates an object.

Because the object has `__call__()`, we can subsequently do:

```python
greet("Mohit")
```

which effectively invokes:

```python
Logger_object.__call__("Mohit")
```

---

# 21. How a Class-Based Decorator Works

The flow is:

```text
Original greet function
        ↓
Logger(greet)
        ↓
Logger object created
        ↓
greet now points to Logger object
        ↓
greet("Mohit")
        ↓
Logger_object.__call__("Mohit")
        ↓
self.func("Mohit")
        ↓
Original greet
```

The important difference from a function decorator:

```text
Function decorator
       ↓
closure stores original function


Class-based decorator
       ↓
object stores original function
       ↓
self.func
```

---

# 22. Why Use a Class-Based Decorator?

One major advantage is that the decorator can maintain **state through instance attributes**.

Example:

```python
class CountCalls:

    def __init__(self, func):
        self.func = func
        self.count = 0

    def __call__(self, *args, **kwargs):
        self.count += 1

        print(f"Call number: {self.count}")

        return self.func(*args, **kwargs)
```

Usage:

```python
@CountCalls
def greet():
    print("Hello")
```

Calling:

```python
greet()
greet()
greet()
```

produces:

```text
Call number: 1
Hello

Call number: 2
Hello

Call number: 3
Hello
```

The state is maintained in:

```python
self.count
```

So:

```text
Class-based decorator
        ↓
Decorator object
        ↓
Instance attributes
        ↓
Persistent state
```

---

# 23. Class-Based Decorator with Arguments

Suppose we want:

```python
@Retry(max_attempts=3)
def call_api():
    ...
```

We can implement:

```python
class Retry:

    def __init__(self, max_attempts):
        self.max_attempts = max_attempts

    def __call__(self, func):

        def wrapper(*args, **kwargs):

            for attempt in range(self.max_attempts):
                try:
                    return func(*args, **kwargs)
                except Exception:
                    print(f"Attempt {attempt + 1} failed")

            raise Exception("All attempts failed")

        return wrapper
```

Usage:

```python
@Retry(max_attempts=3)
def call_api():
    ...
```

This is approximately:

```python
call_api = Retry(max_attempts=3)(call_api)
```

First:

```python
Retry(max_attempts=3)
```

creates the decorator object.

Then:

```python
decorator_object(call_api)
```

invokes:

```python
decorator_object.__call__(call_api)
```

which returns the wrapper.

Conceptually:

```text
Retry(3)
   ↓
Retry object
   ↓
object(call_api)
   ↓
__call__(call_api)
   ↓
wrapper
```

The configuration is stored as:

```python
self.max_attempts
```

---

# 24. Function-Based vs Class-Based Decorators

### Function-based decorator

```python
def decorator(func):

    def wrapper(*args, **kwargs):
        return func(*args, **kwargs)

    return wrapper
```

State/configuration is commonly retained through:

```text
closure
```

### Class-based decorator

```python
class Decorator:

    def __init__(self, func):
        self.func = func

    def __call__(self, *args, **kwargs):
        return self.func(*args, **kwargs)
```

State/configuration is retained through:

```text
instance attributes
```

Mental model:

```text
Function decorator
      ↓
closure-based state


Class-based decorator
      ↓
object/instance-based state
```

# 25. Important Class-Based Decorator Interview Question

If asked:

> **Does a decorator have to be a function?**

Strong answer:

> "No. A decorator can be any callable. A common alternative is a class implementing `__call__()`. An instance of that class can store the decorated function and configuration as instance state, while `__call__()` performs the wrapping behavior."

---

# 26. Class-Based Decorator and Function Metadata

There is a caveat.

With:

```python
@Logger
def greet():
    ...
```

the name `greet` now refers to a `Logger` instance rather than directly to the original function.

Therefore:

```python
greet.__name__
```

doesn't behave like a normal function unless metadata is deliberately exposed/preserved.

This differs from the function-based decorator approach using:

```python
@wraps(func)
```

# 28. Async Decorators

For asynchronous functions, the wrapper generally needs to be asynchronous if it needs to await the decorated function.

Example:

```python
from functools import wraps


def log_execution(func):

    @wraps(func)
    async def wrapper(*args, **kwargs):
        print("Before")

        result = await func(*args, **kwargs)

        print("After")

        return result

    return wrapper
```

Usage:

```python
@log_execution
async def call_llm():
    ...
```

Important:

```python
result = await func(...)
```

rather than:

```python
result = func(...)
```

when the decorated function is async and its result needs to be awaited.

This becomes particularly relevant for production AI/backend systems with asynchronous LLM/API calls.

---

# 29. Production-Quality Generic Decorator

A standard synchronous decorator:

```python
from functools import wraps


def decorator(func):

    @wraps(func)
    def wrapper(*args, **kwargs):

        # Before behavior

        result = func(*args, **kwargs)

        # After behavior

        return result

    return wrapper
```

The important pieces are:

```text
@wraps(func)
      ↓
preserve metadata

*args, **kwargs
      ↓
support arbitrary arguments

return result
      ↓
preserve function output

wrapper
      ↓
add behavior
```

# 30. Interview Traps

### Trap 1 — `decorator` is a keyword

False.

`decorator` is just a conventional function name.

---

### Trap 2 — `@decorator` is magic

False.

Approximately:

```python
@decorator
def f():
    ...
```

becomes:

```python
f = decorator(f)
```

---

### Trap 3 — Decorator executes every time the function is called

Not exactly.

The decorator is **applied at function-definition/declaration time**.

The returned wrapper executes when the decorated function is called.

---

### Trap 4 — Multiple decorators execute bottom-to-top

At runtime, that's backwards.

For:

```python
@A
@B
def f():
    ...
```

application:

```text
B → A
```

runtime:

```text
A → B → f
```

---

### Trap 5 — Forgetting to return the result

Bad:

```python
func(*args, **kwargs)
```

Correct when preserving output:

```python
return func(*args, **kwargs)
```

---

### Trap 6 — Forgetting `@wraps`

Without `@wraps`, the wrapper can replace important metadata of the original function.

---

### Trap 7 — Forgetting `*args, **kwargs`

A decorator that assumes a fixed function signature won't work generically.

---

### Trap 8 — Confusing mutation with decorator replacement

The decorator generally creates/returns another callable:

```text
original function
      ↓
decorator
      ↓
new wrapper callable
```

The original function itself isn't necessarily modified internally.

---

### Trap 9 — Decorators must be functions

False.

Any suitable **callable** can act as a decorator, including a class or class instance with `__call__()`.

---

# 31. Interview-Ready Definition

If asked:

> **What is a decorator in Python?**

A strong answer:

> "A decorator is a callable that takes another callable, adds or modifies its behavior, and returns a callable. The `@decorator` syntax is syntactic sugar for assigning the result of the decorator back to the function name. Decorators commonly use nested wrapper functions and closures and are useful for cross-cutting concerns such as logging, authentication, caching, retries, and instrumentation."

---

# 32. Multiple Decorator Interview Answer

If asked:

> **How are multiple decorators applied?**

Answer:

> "For `@A` followed by `@B`, Python effectively creates `f = A(B(f))`. Therefore B is applied to the original function first, and A is applied to the result. At runtime, A's wrapper executes first, followed by B and then the original function."

---

# 33. Decorator with Arguments Interview Answer

If asked:

> **Why does a decorator with arguments need an extra function level?**

Answer:

> "Because `@decorator(3)` is effectively `f = decorator(3)(f)`. The first call, `decorator(3)`, receives the decorator configuration and must return another callable that can receive the function. That returned callable then creates and returns the wrapper."

---

# 34. Class-Based Decorator Interview Answer

If asked:

> **Can a class be used as a decorator?**

Answer:

> "Yes. A decorator only needs to be callable. A class can be used as a decorator because calling the class creates an instance, and if that instance implements `__call__()`, it can subsequently receive the decorated function. The instance can store the function and configuration as attributes, making class-based decorators useful when the decorator needs state."

---

# 36. Three Rules to Memorize

```text
1. @decorator ≈ f = decorator(f)

2. @A @B ≈ f = A(B(f))

3. @decorator(3) ≈ f = decorator(3)(f)
```

And the most important execution rule:

```text
Bottom decorator → applied first

Top decorator → executes first at runtime
```

Finally:

```text
Function decorator
      ↓
closure commonly stores state


Class-based decorator
      ↓
object/instance commonly stores state
```

These transformations are the core of most Python decorator interview questions.

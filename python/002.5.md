Python — Topic 2.5: OOP Fundamentals

1. Class vs Object

A class is a blueprint defining the data and behavior that objects can have.

An object is an actual instance of a class.

class Employee:
    def __init__(self, name, role):
        self.name = name
        self.role = role

    def introduce(self):
        return f"I am {self.name}, working as {self.role}"

e1 = Employee("Mohit", "AI Engineer")
e2 = Employee("Rahul", "Backend Engineer")

Here:

- "Employee" → class
- "e1", "e2" → objects/instances
- Both objects have independent instance state.

Conceptually:

Employee (class)
     |
     +--- e1
     |     name = Mohit
     |     role = AI Engineer
     |
     +--- e2
           name = Rahul
           role = Backend Engineer

---

2. "__new__" vs "__init__"

"__init__" initializes an already-created object. It does not actually create the object.

Conceptually:

Class(...)
   |
   v
__new__()
   |
   v
object created
   |
   v
__init__()
   |
   v
object initialized

Normally we only override "__init__".

"__new__" is used for more advanced object-creation behavior, such as immutable types, custom object creation, or some singleton/metaclass patterns.

---

3. "self"

"self" refers to the current instance.

class Employee:
    def introduce(self):
        return self.name

When:

e1.introduce()

is called, it is conceptually equivalent to:

Employee.introduce(e1)

Therefore "self" receives "e1".

"self" is not a Python keyword. It is a convention.

Technically:

class Employee:
    def introduce(current_object):
        return current_object.name

would work, but "self" should always be used as the conventional name.

---

4. Method Binding

A function defined in a class becomes a bound method when accessed through an instance.

class A:
    def show(self):
        print("hello")

a = A()

These are conceptually related:

a.show()

and:

A.show(a)

"A.show" is the underlying function.

"a.show" is a bound method with "a" already bound as "self".

A.show
   |
   v
function expecting self

a.show
   |
   v
bound method
   |
   v
self = a

Therefore:

A.show()

fails because no instance is supplied for "self".

But:

A.show(a)

works because "a" is explicitly supplied.

---

5. Instance Attributes vs Class Attributes

Instance attribute

class Employee:
    def __init__(self, name):
        self.name = name

Each object gets its own "name".

e1 = Employee("Mohit")
e2 = Employee("Rahul")

e1.name = "Amit"

print(e1.name)  # Amit
print(e2.name)  # Rahul

---

Class attribute

class Employee:
    company = "Samsung"

    def __init__(self, name):
        self.name = name

"company" belongs to the class.

Instances can access it:

e1.company
e2.company
Employee.company

Important shadowing behavior

class A:
    x = 10

a = A()
a.x = 20

Now:

A.x  # 10
a.x  # 20

"a.x = 20" creates an instance attribute named "x"; it does not modify "A.x".

To modify the class attribute:

A.x = 20

Attribute lookup

Roughly, Python looks for attributes on the instance and then through its class hierarchy.

---

6. Instance Method vs Class Method vs Static Method

Instance method

Receives "self" automatically.

class User:
    def get_name(self):
        return self.name

Used when working with a particular object.

---

Class method

Uses "@classmethod" and receives "cls" automatically.

class User:
    @classmethod
    def create(cls, name):
        return cls(name)

"cls" represents the class on which the method is invoked.

Common use: alternative constructor

class User:
    def __init__(self, name):
        self.name = name

    @classmethod
    def from_string(cls, data):
        return cls(data.strip())

user = User.from_string("Mohit")

Class methods are also useful because "cls" respects inheritance:

class Admin(User):
    pass

Admin.from_string("Mohit")

The "cls" can be "Admin", allowing the constructor to create an "Admin".

---

Static method

Uses "@staticmethod".

It receives neither "self" nor "cls" automatically.

class User:

    @staticmethod
    def is_valid_name(name):
        return bool(name and name.strip())

Usage:

User.is_valid_name("Mohit")

A static method is essentially a function logically grouped inside a class.

Key distinction

Instance method → self automatically
Class method    → cls automatically
Static method   → nothing automatically

Important terminology

Python does not have a separate "static variable" keyword like Java/C++.

The closest equivalent is a class variable/class attribute.

Also:

Python class variable → Java/C++ static variable
Python @staticmethod  → Java/C++ static method
Python @classmethod   → no exact Java/C++ equivalent

---

7. Inheritance

Inheritance allows a child/subclass to reuse and extend a parent/base class.

class Animal:
    def speak(self):
        print("Animal speaks")


class Dog(Animal):
    pass

Dog().speak()

prints:

Animal speaks

The method isn't defined in "Dog", so Python searches the class hierarchy.

---

8. Method Overriding

A child class can provide its own implementation of an inherited method.

class Animal:
    def speak(self):
        print("Animal")


class Dog(Animal):
    def speak(self):
        print("Dog")

Dog().speak()

prints:

Dog

Python finds "speak()" in "Dog" first and stops there.

The parent implementation still exists and can be accessed explicitly:

Animal.speak(dog)

---

9. "super()"

"super()" allows us to continue lookup through the inheritance hierarchy according to the MRO.

class Animal:
    def speak(self):
        print("Animal")


class Dog(Animal):
    def speak(self):
        print("Dog")
        super().speak()

Output:

Dog
Animal

Important:

"super()" does not simply mean "my parent."

The precise rule is:

«"super()" continues lookup from the next class in the MRO.»

In simple inheritance:

Dog → Animal → object

so it looks like "parent."

With multiple inheritance, it can be another sibling class in the MRO.

---

10. Constructor + "super()"

A child can reuse the parent's initialization:

class Employee:
    def __init__(self, name):
        self.name = name


class AIEngineer(Employee):
    def __init__(self, name, model):
        super().__init__(name)
        self.model = model

Now:

e = AIEngineer("Mohit", "Gemini")

The parent initializes "name", while the child initializes "model".

---

11. Polymorphism

Polymorphism means different objects can be used through the same interface/operation while providing different behavior.

class Dog:
    def speak(self):
        return "Bark"


class Cat:
    def speak(self):
        return "Meow"


def make_sound(animal):
    return animal.speak()

make_sound(Dog())  # Bark
make_sound(Cat())  # Meow

The caller doesn't need to know the concrete class.

---

12. Duck Typing

Python does not require inheritance for polymorphism.

class Duck:
    def quack(self):
        print("Quack")


class Person:
    def quack(self):
        print("Person pretending to be a duck")


def make_it_quack(obj):
    obj.quack()

Both work:

make_it_quack(Duck())
make_it_quack(Person())

This is duck typing.

The philosophy is roughly:

«If an object provides the required behavior, use it.»

Distinction

Polymorphism
    ↓
Different objects support the same operation/interface

Duck typing
    ↓
Python determines usability based on behavior rather than
requiring a specific class hierarchy

Duck typing is therefore a common way Python implements polymorphic behavior.

---

13. Inheritance vs Duck Typing

Inheritance:

class Animal:
    def speak(self):
        ...


class Dog(Animal):
    ...

gives you:

- explicit relationship
- shared behavior
- explicit contract
- common type hierarchy

Duck typing:

class Dog:
    def speak(self):
        ...


class Cat:
    def speak(self):
        ...

allows flexible use without requiring inheritance.

We don't necessarily need a base class just because classes have similar behavior.

---

14. Composition vs Inheritance

Inheritance = "is-a"

class Dog(Animal):
    ...

A Dog is an Animal.

Composition = "has-a"

class Car:
    def __init__(self, engine):
        self.engine = engine

A Car has an Engine.

Usually:

Car → Engine

is composition, while:

Dog → Animal

is inheritance.

Why composition is often preferable

Composition provides loose coupling and makes components easier to replace.

class Car:
    def __init__(self, engine):
        self.engine = engine

Now we can inject different implementations:

Car(GasEngine())
Car(ElectricEngine())

This is particularly useful in production systems.

For AI systems, an agent may have:

- LLM client
- MCP client
- retriever
- database client
- tool registry

Those components generally shouldn't be parent classes of the agent.

15. "@property"

A property allows a method to be accessed like an attribute.

class Employee:
    def __init__(self, salary):
        self._salary = salary

    @property
    def salary(self):
        return self._salary

Usage:

employee.salary

instead of:

employee.salary()

The property getter is executed behind the scenes.

---

Property setter

class Employee:
    def __init__(self, salary):
        self._salary = salary

    @property
    def salary(self):
        return self._salary

    @salary.setter
    def salary(self, value):
        if value < 0:
            raise ValueError("Salary cannot be negative")

        self._salary = value

Now:

employee.salary = 50000

passes through the setter.

But:

employee.salary = -5000

raises an error.

Why use properties?

Properties provide:

- controlled access
- validation
- computed attributes
- read-only attributes
- ability to change internal implementation without changing the external API

Important

"_salary" is an instance attribute.

The "_" is a convention indicating internal use; Python does not enforce true private access.

A property does not simply mean "private variable."

---

16. Read-only Properties

If no setter is defined:

class Account:
    @property
    def account_id(self):
        return self._account_id

The property can be read:

account.account_id

but cannot normally be assigned through the property:

account.account_id = ...

---

17. Abstract Base Classes (ABC)

Python provides "abc" for defining formal contracts.

from abc import ABC, abstractmethod

class Animal(ABC):

    @abstractmethod
    def speak(self):
        pass

You cannot instantiate the abstract class:

Animal()  # TypeError

A concrete subclass must implement the abstract method:

class Dog(Animal):

    def speak(self):
        return "Bark"

Now:

Dog()

works.

---

ABC vs "NotImplementedError"

Without ABC:

class Animal:
    def speak(self):
        raise NotImplementedError

Python allows:

Animal()

The error only occurs when the method is actually invoked.

With ABC:

class Animal(ABC):
    @abstractmethod
    def speak(self):
        pass

Python prevents instantiation of the incomplete class.

Why use ABC?

It provides an explicit and enforced contract.

Useful in large production codebases where multiple implementations must follow a common interface.

---

18. Abstract Classes Can Have Concrete Methods

An ABC can contain normal implementations too:

class LLM(ABC):

    @abstractmethod
    def generate(self, prompt):
        pass

    def log_request(self, prompt):
        print(prompt)

Child classes must implement "generate()" but automatically inherit "log_request()".

Therefore an abstract class can provide:

- contract
- shared behavior
- shared state

19. Dataclasses

Dataclasses are useful when a class primarily represents structured data.

Instead of:

class Employee:
    def __init__(self, name, salary, role):
        self.name = name
        self.salary = salary
        self.role = role

we can use:

from dataclasses import dataclass

@dataclass
class Employee:
    name: str
    salary: float
    role: str

Python automatically generates useful methods including:

- "__init__"
- "__repr__"
- "__eq__"

---

Dataclass and type annotations

@dataclass
class Employee:
    name: str
    salary: float

Type annotations document expected types and help tooling.

Dataclasses themselves do not provide full runtime type validation.

This differs from Pydantic, which we'll cover later.

---

20. Dataclass Mutable Defaults

Avoid:

@dataclass
class Team:
    members: list = []

Use:

from dataclasses import dataclass, field

@dataclass
class Team:
    members: list = field(default_factory=list)

"default_factory" creates a new list for each instance.

t1 = Team()
t2 = Team()

t1.members.append("Mohit")

print(t1.members)  # ["Mohit"]
print(t2.members)  # []

This is related to Python's mutable-default trap.

---

21. "frozen=True"

Dataclasses can be made effectively immutable:

@dataclass(frozen=True)
class Point:
    x: int
    y: int

Then:

p.x = 30

raises an error.

Useful for value-like objects whose state shouldn't change after creation.

22. Dunder / Magic Methods

Dunder methods are special methods with double underscores.

Examples:

__init__
__str__
__repr__
__eq__
__len__
__getitem__
__iter__

They allow objects to participate naturally in Python's protocols.

---

23. "__str__"

Provides a human-friendly string representation.

class User:
    def __init__(self, name):
        self.name = name

    def __str__(self):
        return f"User: {self.name}"

Then:

print(user)

uses the string representation.

---

24. "__repr__"

Provides a developer/debugging-oriented representation.

class User:
    def __init__(self, name):
        self.name = name

    def __repr__(self):
        return f"User(name={self.name!r})"

repr(user)

might return:

User(name='Mohit')

Difference

__str__
    ↓
human-friendly

__repr__
    ↓
developer/debugging representation

If "__str__" isn't provided, Python can fall back to "__repr__".

If neither is customized, you'll typically see a default representation such as:

<__main__.User object at 0x...>

---

25. "__eq__"

Controls equality using "==".

class User:
    def __init__(self, name):
        self.name = name

    def __eq__(self, other):
        return self.name == other.name

Now two different objects can be equal based on their values.

Dataclasses generate value-based "__eq__" automatically by default.

---

26. Other Useful Dunder Methods

"__len__"

Controls:

len(obj)

Example:

class Team:
    def __init__(self, members):
        self.members = members

    def __len__(self):
        return len(self.members)

---

"__getitem__"

Controls:

obj[index]

Example:

class Team:
    def __init__(self, members):
        self.members = members

    def __getitem__(self, index):
        return self.members[index]

---

"__iter__"

Allows an object to participate in iteration:

for member in team:
    ...

Iteration protocols will be covered in depth in Topic 3.

27. MRO — Method Resolution Order

MRO determines the order in which Python searches classes for attributes and methods.

For:

class A:
    pass

class B(A):
    pass

class C(B):
    pass

the MRO is:

C → B → A → object

You can inspect it using:

C.__mro__

or:

C.mro()

When:

C().some_method()

is called, Python searches according to this order.

---

28. "object"

In Python 3, normal classes ultimately derive from "object".

Therefore:

C → B → A → object

"object" is the root/base class of the normal Python class hierarchy.

---

29. Multiple Inheritance

Python supports multiple inheritance:

class A:
    pass

class B:
    pass

class C(A, B):
    pass

Here "C" inherits from both "A" and "B".

The MRO determines the search order.

---

30. Diamond Inheritance

A classic structure:

      A
     / \
    B   C
     \ /
      D

Code:

class A:
    def show(self):
        print("A")

class B(A):
    pass

class C(A):
    pass

class D(B, C):
    pass

The MRO is:

D → B → C → A → object

This prevents ambiguity and gives Python a deterministic lookup order.

---

31. C3 Linearization

C3 linearization is the algorithm Python uses to calculate a consistent MRO, especially with multiple inheritance.

It ensures important ordering constraints such as:

1. A child appears before its parent.
2. The order specified in the inheritance list is respected.
3. Parent-class ordering remains consistent.

For:

class D(B, C):
    pass

Python can produce:

D → B → C → A → object

You don't generally need to manually calculate the C3 algorithm unless specifically asked.

Mental model

C3 linearization
       ↓
calculates MRO
       ↓
MRO determines lookup order
       ↓
super() follows that order

32. "super()" in Multiple Inheritance

Consider:

class A:
    def show(self):
        print("A")


class B(A):
    def show(self):
        print("B")
        super().show()


class C(A):
    def show(self):
        print("C")
        super().show()


class D(B, C):
    def show(self):
        print("D")
        super().show()

MRO:

D → B → C → A → object

Therefore:

D().show()

outputs:

D
B
C
A

Why?

D.show()
   ↓
super()
   ↓
B.show()
   ↓
super()
   ↓
C.show()
   ↓
super()
   ↓
A.show()

The crucial point:

«"super()" means "continue from the next class in the MRO", not simply "call my parent."»

33. Overriding vs Overloading

Overriding

A child class provides a new implementation of an inherited method.

class A:
    def show(self):
        ...


class B(A):
    def show(self):
        ...

---

Overloading

Traditionally means:

«Same method name with different parameter signatures.»

For example, Java/C++ can have:

add(int, int)
add(int, int, int)

Python does not support traditional compile-time method overloading by defining the same method multiple times.

class Calculator:
    def add(self, a, b):
        ...

    def add(self, a, b, c):
        ...

The second "add()" replaces the first.

Python commonly achieves similar behavior with:

def add(self, a, b, c=0):
    ...

or:

def add(self, *args):
    ...

34. Production Design Takeaways

Prefer inheritance when:

- There is a genuine "is-a" relationship.
- Subclasses genuinely conform to the parent abstraction.
- Shared behavior is meaningful.
- Polymorphism through a common hierarchy is useful.

Prefer composition when:

- There is a "has-a" relationship.
- Components need to be replaceable.
- You want loose coupling.
- Dependency injection is useful.
- You don't want unnecessary inheritance coupling.

Use ABC when:

- You want an explicit/enforced contract.
- Multiple implementations need consistent APIs.

Use duck typing when:

- You want flexible behavior-based interfaces.
- A formal inheritance hierarchy isn't necessary.

Use dataclasses when:

- The class primarily represents data/state.
- You want generated initialization, representation, and equality methods.

Use properties when:

- A value needs validation.
- A value is computed.
- You want controlled/read-only access.
- You want an attribute-like API around internal logic.

Python Topic 3 — Iterators, Generators, Exceptions & Context Managers

1. Iterable vs Iterator

Iterable

An iterable is an object from which we can obtain an iterator, generally by implementing "__iter__()".

Examples:

numbers = [1, 2, 3]
t = (1, 2, 3)

A list/tuple is iterable but is not itself an iterator.

next(numbers)  # TypeError

We first obtain an iterator:

it = iter(numbers)
next(it)       # 1

Iterator

An iterator:

- Maintains iteration state.
- Produces values one at a time.
- Implements "__iter__()" and "__next__()".
- "__next__()" returns the next value.
- Raises "StopIteration" when exhausted.

numbers = [10, 20, 30]

it = iter(numbers)

next(it)  # 10
next(it)  # 20
next(it)  # 30
next(it)  # StopIteration

Iterator protocol

iterator = iter(iterable)

while True:
    try:
        value = next(iterator)
    except StopIteration:
        break

A "for" loop essentially handles this iteration protocol automatically.

Important distinction

Iterable
   |
   | iter()
   ↓
Iterator
   |
   | next()
   ↓
Next value

Multiple iterators over the same iterable

numbers = [1, 2, 3]

it1 = iter(numbers)
it2 = iter(numbers)

"it1" and "it2" are different iterator objects with independent state.

next(it1)  # 1
next(it1)  # 2

next(it2)  # 1

Moving "it1" does not affect "it2".

2. Generators

A generator is a convenient way to create an iterator, usually using "yield".

def numbers():
    yield 1
    yield 2
    yield 3

Calling the generator function:

g = numbers()

creates a generator object.

Important

The function body does not execute immediately.

Execution starts when:

next(g)

is called.

def gen():
    print("Hello")
    yield 10

g = gen()       # body hasn't executed

next(g)         # prints Hello, returns 10

Why?

A generator is designed for lazy execution.

gen()
  ↓
Generator object
  ↓
next()
  ↓
Execute until yield
  ↓
Return yielded value
  ↓
Pause and preserve state

---

3. "yield" vs "return"

"return" terminates a normal function.

def f():
    return 10

"yield" temporarily suspends a generator.

def f():
    yield 10
    yield 20

Example:

def counter():
    x = 0

    while x < 3:
        yield x
        x += 1

Execution:

next(g)
  ↓
x = 0
yield x
  ↓
returns 0
  ↓
generator pauses

next(g)
  ↓
resume after yield
  ↓
x += 1
  ↓
yield 1

The generator preserves:

- Local variables
- Execution position
- Generator state

Important wording

A generator doesn't simply maintain a "pointer".

It preserves its execution frame/state, including local variables and the point at which execution should resume.

---

4. Generator Expressions

A generator expression uses:

(expression for item in iterable)

Example:

g = (x * x for x in range(10))

This creates a generator object.

Compare:

[x * x for x in range(10)]

→ List comprehension → creates the list.

(x * x for x in range(10))

→ Generator expression → lazy evaluation.

Nothing is calculated until values are requested.

g = (x * x for x in range(10))

next(g)  # 0
next(g)  # 1
next(g)  # 4

Important

Parentheses alone don't mean "generator".

This specific syntax creates a generator:

(expression for item in iterable)

---

5. Generators are Iterators

A generator is itself an iterator.

Therefore:

g = (x for x in range(3))

iter(g) is g

returns:

True

This is an important interview trap.

Compare with a list

numbers = [1, 2, 3]

iter(numbers) is iter(numbers)

Normally:

False

because each "iter(numbers)" creates a new iterator.

For a generator:

g = (x for x in range(3))

it1 = iter(g)
it2 = iter(g)

it1 is it2

returns:

True

Both variables refer to the same generator object.

Table

Object| "iter(obj)"| Independent iterator each time?
List| New iterator| Yes
Tuple| New iterator| Yes
Generator| Itself| No

---

6. Generator Exhaustion

Generators are generally single-use.

g = (x for x in range(3))

list(g)
# [0, 1, 2]

list(g)
# []

Once exhausted, the same generator cannot restart.

A new generator must be created:

list(x for x in range(3))

or:

g = (x for x in range(3))

again.

"for" loop trap

def gen():
    yield 1
    yield 2
    yield 3

g = gen()

for x in g:
    print(x)

for x in g:
    print(x)

Output:

1
2
3

The second loop produces nothing because the generator has already been consumed.

---

7. "yield from"

"yield from" delegates yielding to another iterable/generator.

def numbers():
    yield from [1, 2, 3]

This is conceptually similar to:

def numbers():
    for x in [1, 2, 3]:
        yield x

Therefore:

list(numbers())

gives:

[1, 2, 3]

Generator composition

def first():
    yield 1
    yield 2

def second():
    yield 3
    yield 4

def combined():
    yield from first()
    yield from second()

Result:

list(combined())
# [1, 2, 3, 4]

Important trap

These are different:

yield from [1, 2, 3]

Produces:

1
2
3

while:

yield [1, 2, 3]

produces one value:

[1, 2, 3]

Therefore:

list(generator_using_yield_from)
# [1, 2, 3]

versus:

list(generator_using_yield)
# [[1, 2, 3]]

---

8. Generator "send()"

Generators can communicate in both directions.

Normally:

Generator → Consumer
    yield value

With "send()":

Generator ← Consumer
    send(value)

Example:

def receiver():
    value = yield
    print("Received:", value)

g = receiver()

next(g)       # Start generator and reach yield
g.send(100)   # Sends 100 into paused yield

Output:

Received: 100

Why "next()" is required first

This won't work:

g = receiver()
g.send(100)

because the generator hasn't reached its first "yield".

Start it first:

g = receiver()
next(g)
g.send(100)

Mental model

             yielded value
Generator ─────────────────→ Consumer

Generator ←───────────────── Consumer
              send(value)

9. Exceptions

An exception represents a condition where normal execution cannot continue in the current way.

Example:

x = 10 / 0

raises:

ZeroDivisionError

---

10. "try / except"

try:
    x = 10 / 0
except ZeroDivisionError:
    print("Cannot divide by zero")

You can capture the exception:

try:
    x = 10 / 0
except ZeroDivisionError as e:
    print(e)

Multiple exceptions

try:
    x = int(input())
    result = 10 / x
except ValueError:
    print("Invalid number")
except ZeroDivisionError:
    print("Cannot divide by zero")

Or:

except (ValueError, TypeError):
    ...

---

11. "else"

"else" executes only when the "try" block completes successfully.

try:
    result = 10 / 2
except ZeroDivisionError:
    print("Error")
else:
    print("Success:", result)

Output:

Success: 5.0

If an exception occurs inside "try", "else" is skipped.

---

12. "finally"

"finally" normally executes regardless of whether an exception occurs.

try:
    process()
except Exception:
    handle_error()
finally:
    cleanup()

Common uses:

- Closing resources
- Releasing locks
- Cleanup
- Transaction/resource handling

Execution pattern

try
 ↓
exception?
 ↓ yes
except
 ↓
finally

If no exception:

try
 ↓
else
 ↓
finally

---

13. "raise"

You can explicitly raise an exception:

def withdraw(balance, amount):
    if amount > balance:
        raise ValueError("Insufficient balance")

Re-raise

Inside an "except":

try:
    process()
except ValueError:
    log_error()
    raise

A bare "raise" re-raises the currently handled exception.

New exception

raise ValueError("Invalid input")

raises a new exception.

Summary

raise
    → re-raise current exception

raise SomeError(...)
    → raise a new exception

---

14. Custom Exceptions

Create application-specific exceptions by inheriting from "Exception".

class UserNotFoundError(Exception):
    pass

Then:

raise UserNotFoundError("User does not exist")

Exception hierarchy

class AppError(Exception):
    pass

class DatabaseError(AppError):
    pass

class ValidationError(AppError):
    pass

Hierarchy:

Exception
   ↓
AppError
   ├── DatabaseError
   └── ValidationError

This allows broad handling:

except AppError:
    ...

to catch both child exceptions.

---

15. "except" Matching Order

Python checks "except" blocks top to bottom.

Only the first matching handler executes.

Correct:

try:
    process()
except DatabaseError:
    ...
except AppError:
    ...
except Exception:
    ...

If:

DatabaseError → AppError → Exception

then "DatabaseError" should come first.

Bad ordering:

except Exception:
    ...
except DatabaseError:
    ...

The "DatabaseError" handler will never be reached for a "DatabaseError", because "Exception" already matches it.

Interview rule

«Put specific exception handlers before general/parent exception handlers.»

---

16. Exception Chaining

You can explicitly establish that one exception caused another:

try:
    save_to_database()
except DatabaseError as e:
    raise ServiceError("Unable to save user") from e

"from e" tells Python:

«The new "ServiceError" was caused by the original exception "e".»

Conceptually:

DatabaseError
      ↓ caused
ServiceError

Without "from"

except DatabaseError:
    raise ServiceError("Unable to save user")

The original exception can still exist as exception context, but "from e" explicitly establishes it as the cause.

"from None"

raise ServiceError("Operation failed") from None

This suppresses the displayed underlying exception context.

---

17. Exception-handling Best Practices

Avoid bare "except"

Avoid:

except:
    pass

It can catch things such as "KeyboardInterrupt" and "SystemExit".

Prefer specific exceptions:

except ValueError:
    ...

or, when genuinely appropriate:

except Exception as e:
    logger.exception("Processing failed")
    raise

Don't silently swallow exceptions

Bad:

try:
    process()
except Exception:
    pass

This can hide failures and cause silent data problems.

Catch the most specific exception possible

Prefer:

except TimeoutError:
    retry()

over:

except Exception:
    retry()

Not every exception is retryable.

This is especially important for:

- LLM calls
- MCP calls
- Network requests
- Database operations

Don't use exceptions for ordinary control flow unnecessarily

Instead of:

try:
    value = data["name"]
except KeyError:
    value = "Unknown"

you could use:

value = data.get("name", "Unknown")

when absence is an expected condition.

---

18. "finally" Trap

"finally" can override a return value.

def test():
    try:
        return 10
    finally:
        return 20

Returns:

20

Even an exception can be suppressed:

def test():
    try:
        raise ValueError("Error")
    finally:
        return 10

This returns "10" instead of propagating the exception.

Best practice

Avoid "return", "break", or "continue" in "finally" unless you have a very specific reason.

---

19. Context Managers

Context managers manage resources reliably.

Common examples:

- Files
- Database connections
- Locks
- Network resources
- Transactions

Example:

with open("data.txt") as file:
    data = file.read()

The resource is cleaned up when leaving the "with" block, including when an exception occurs.

---

20. "__enter__" and "__exit__"

A class-based context manager implements:

__enter__()
__exit__()

Example:

class MyContext:
    def __enter__(self):
        print("Entering")
        return self

    def __exit__(self, exc_type, exc_value, traceback):
        print("Exiting")

Usage:

with MyContext() as obj:
    print("Inside")

Output:

Entering
Inside
Exiting

"as obj"

The value returned by:

__enter__()

is assigned to:

obj

---

21. Exception Handling in "__exit__"

If an exception occurs inside the "with" block:

__exit__(exc_type, exc_value, traceback)

receives information about it.

For example:

exc_type
    → ValueError

exc_value
    → ValueError("error")

traceback
    → traceback object

Suppressing exceptions

If "__exit__()" returns "True":

def __exit__(self, exc_type, exc_value, traceback):
    return True

the exception is suppressed.

If it returns "False" or "None", the exception propagates.

Example

class IgnoreError:
    def __enter__(self):
        pass

    def __exit__(self, exc_type, exc_value, traceback):
        return True

with IgnoreError():
    raise ValueError("Oops")

print("Continues")

Output:

Continues

22. Context Managers and Cleanup

Conceptually:

with resource:
    work()

provides behavior similar to:

resource.__enter__()

try:
    work()
finally:
    resource.__exit__(...)

The actual language semantics are more precise, but this is a useful mental model.

---

23. "@contextmanager"

Python provides a simpler way to create context managers:

from contextlib import contextmanager

@contextmanager
def my_context():
    print("enter")
    yield
    print("exit")

Usage:

with my_context():
    print("inside")

Output:

enter
inside
exit

Structure

@contextmanager
def something():
    # setup
    yield
    # cleanup

Think:

setup
 ↓
yield
 ↓
with-block
 ↓
cleanup

Resource example

@contextmanager
def resource():
    connection = create_connection()

    try:
        yield connection
    finally:
        connection.close()

Usage:

with resource() as conn:
    conn.execute(...)

The yielded connection becomes "conn".

The "finally" guarantees cleanup.

---

24. Multiple Context Managers

You can manage multiple resources:

with open("input.txt") as src, open("output.txt", "w") as dst:
    data = src.read()
    dst.write(data)

---

25. Nested Context Managers

Example:

with lock:
    with database:
        update()

If "update()" raises an exception, contexts are exited in reverse order.

Enter lock
    ↓
Enter database
    ↓
update()
    ↓
Exit database
    ↓
Exit lock

This is LIFO — Last In, First Out.

It is important because inner resources can depend on outer resources.

---

26. Context Managers for Locks

A common concurrency pattern:

with lock:
    shared_data.update(...)

Conceptually:

Acquire lock
     ↓
Critical section
     ↓
Release lock

Even if an exception occurs, the context manager ensures the lock is released.

---

27. Database Transactions

Context managers are also useful for transactions.

Conceptually:

Enter transaction
       ↓
Execute operations
       ↓
Success → commit
Failure → rollback
       ↓
Exit

Exact behavior depends on the database library.

Trap 2 — Same iterable, different iterators

Trap 3 — Generator is its own iterator

---

Trap 4 — Generator is exhausted

g = (x for x in range(3))

# [0, 1, 2]

---

Trap 5 — "yield" vs "yield from"

yield [1, 2, 3]

→ one value.

yield from [1, 2, 3]

→ three values.

---

Trap 6 — "else"

"else" runs only if the "try" block completes without an exception.

---

Trap 7 — "finally"

"finally" normally runs regardless of exception.

But a "return" inside "finally" can override a return or suppress an exception.

---

Trap 8 — Exception order

Specific handlers must generally come before general handlers.

except DatabaseError:
    ...

except AppError:
    ...

except Exception:
    ...

---

Trap 9 — "raise" vs new exception

raise

→ re-raises current exception.

raise ValueError(...)

→ raises a new exception.

---

Trap 10 — "raise ... from ..."

raise ServiceError(...) from e

→ explicitly establishes "e" as the cause of the new exception.

---

Trap 11 — "__exit__" return value

return True

→ suppress exception.

return False

or:

return None

→ exception propagates.

---

Trap 12 — Nested context managers

Contexts exit in reverse order:

Enter A
Enter B
Exit B
Exit A

Senior Interview Summary

If asked to explain the whole topic concisely:

«An iterable is an object from which an iterator can be obtained, while an iterator maintains iteration state and implements "__next__()". Generators are a convenient way to implement iterators using "yield", providing lazy evaluation and preserving execution state between calls. "yield from" delegates iteration to another iterable or generator. Python exceptions are handled using "try", "except", "else", and "finally"; "raise" can create or re-raise exceptions, while "raise ... from ..." establishes exception causality. Context managers provide reliable resource management through "__enter__" and "__exit__", or conveniently through "@contextmanager".»

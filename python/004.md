Python Async & Concurrency — Interview Notes

4.1 Concurrency Fundamentals

Concurrency vs Parallelism

Concurrency

- Multiple tasks make progress during overlapping time periods.
- Tasks don't necessarily execute simultaneously.
- Example: one task waits for I/O while another executes.

Parallelism

- Multiple tasks execute simultaneously on multiple CPU cores.

Concurrency:
A ──wait──→ A
      B ──→ B

Parallelism:
Core 1: A ─────────
Core 2: B ─────────

I/O-bound vs CPU-bound

I/O-bound

- Waiting for network, DB, filesystem, APIs, etc.
- Common approaches:
  - "asyncio"
  - threading

CPU-bound

- Heavy computation.
- Common approach:
  - multiprocessing
  - native libraries that release the GIL

Main approaches

Approach| Best suited for
"asyncio"| Large number of async I/O operations
Threading| Blocking I/O / synchronous libraries
Multiprocessing| CPU-heavy Python work

---

4.2 GIL

The Global Interpreter Lock (GIL) in traditional/current standard CPython execution means that only one thread at a time executes Python bytecode within a given interpreter.

Important consequences

CPU-bound pure-Python threads don't achieve true parallel execution within the same interpreter because of the GIL.

However, the GIL does not make threading useless.

Blocking I/O can release the GIL, so threads are useful for I/O-bound work.

Native extensions can also release the GIL.

CPU-bound example

# CPU-heavy pure Python
def calculate():
    ...

Using many threads doesn't necessarily give CPU parallelism.

Use multiprocessing:

from concurrent.futures import ProcessPoolExecutor

Each process has:

- its own interpreter
- its own memory
- its own GIL

Therefore multiple processes can execute Python code in parallel.

Important trap

«GIL ≠ application-level synchronization.»

Even with the GIL, race conditions can occur.

The GIL protects interpreter execution at a lower level; it does not make a multi-step application operation atomic.

---

4.3 Threading

A thread is an execution path inside a process.

Threads in the same process share:

- memory
- global state
- file descriptors
- other process resources

but have their own execution state/stack.

Creating a thread

import threading

def worker():
    print("working")

t = threading.Thread(target=worker)
t.start()
t.join()

"start()" vs "run()"

t.start()

creates/schedules a separate thread.

t.run()

directly executes the target in the current thread; it does not create a new thread.

"join()"

t.join()

means:

«Wait until this thread finishes.»

---

Race Condition

Example:

counter += 1

This is logically:

read counter
add 1
write counter

Two threads can interleave these operations and lose updates.

Protect with Lock

lock = threading.Lock()

with lock:
    counter += 1

Common synchronization primitives

Lock

- One thread at a time.

RLock

- Reentrant lock.
- Same thread can acquire it multiple times.

Semaphore

- Allows up to N concurrent entrants.

sem = threading.Semaphore(5)

Event

- Used for signaling between threads.

ThreadPoolExecutor

Useful for bounded execution of blocking I/O:

from concurrent.futures import ThreadPoolExecutor

with ThreadPoolExecutor(max_workers=10) as executor:
    ...

Threading traps

- Too many threads → memory/context-switching overhead.
- Locks → possible deadlocks.
- Large critical sections → lock contention.
- GIL → CPU-bound pure Python doesn't scale across threads.

---

4.4 Multiprocessing

Multiprocessing uses separate processes.

Each process has:

- separate memory
- separate interpreter
- separate GIL
- independent execution state

Therefore CPU-heavy pure Python can execute in parallel.

Process pool

from concurrent.futures import ProcessPoolExecutor

with ProcessPoolExecutor(max_workers=8) as executor:
    ...

For an 8-core machine, a pool around the number of available CPU cores can be a reasonable starting point, but it should be tuned for the workload.

Important correction

8 CPU cores does not mean the machine can only have 8 processes.

You can have many processes, but only a limited number can execute simultaneously according to available CPU execution capacity.

A process pool avoids creating excessive processes and reuses workers.

Inter-process communication

Because processes don't normally share memory:

- "multiprocessing.Queue"
- "Pipe"
- shared memory
- "Value"
- "Array"
- "Manager"

can be used for communication/shared state.

Multiprocessing vs threading

| Threading| Multiprocessing
Memory| Shared| Separate
GIL| Same interpreter GIL| Separate GIL per process
CPU parallelism| Limited for pure Python| Yes
I/O| Excellent| Usually unnecessary
Creation overhead| Lower| Higher
Communication| Easier| IPC required

---

4.5 Asyncio Fundamentals & Event Loop

"asyncio" is Python's framework for asynchronous I/O.

Core concepts:

Event Loop
    ↓
Coroutines
    ↓
Tasks
    ↓
Awaitables/Futures

Coroutine function

async def fetch():
    return "data"

Calling:

coro = fetch()

creates a coroutine object.

The function body doesn't execute normally just because you called it.

"await"

result = await fetch()

means the current coroutine waits for the awaited operation.

If the awaited operation needs to wait for I/O, the coroutine suspends and the event loop can execute other ready tasks.

Important trap

"async def" alone doesn't make code non-blocking.

Bad:

async def work():
    time.sleep(5)

"time.sleep()" blocks the event-loop thread.

Good:

async def work():
    await asyncio.sleep(5)

"asyncio.sleep()" cooperatively yields to the event loop.

---

Sequential vs concurrent async

Sequential:

await task("A")
await task("B")

If each takes 2 seconds:

A: |----2s----|
B:            |----2s----|

Total ≈ 4s

Concurrent:

await asyncio.gather(
    task("A"),
    task("B")
)

A: |----2s----|
B: |----2s----|

Total ≈ 2s

Critical point

«"await" does not automatically mean concurrency.»

Concurrency requires multiple tasks/coroutines that can be scheduled.

---

Event Loop

The event loop:

1. Finds ready work.
2. Runs a coroutine.
3. The coroutine reaches an "await" that suspends it.
4. The loop runs another ready task.
5. When I/O/timer completes, the suspended task becomes runnable again.

Asyncio is generally cooperative:

Task A
  ↓
await I/O
  ↓
suspend
  ↓
Event Loop
  ↓
Task B

"asyncio.run()"

Typical top-level entry:

asyncio.run(main())

It manages the event loop for the top-level async program.

---

4.6 Coroutines, Tasks & Futures

Coroutine

async def work():
    return 100

coro = work()

"coro" is a coroutine object.

It represents async work but isn't independently scheduled as a Task.

---

Task

task = asyncio.create_task(work())

A Task schedules a coroutine to run on the event loop.

Mental model:

Coroutine
    ↓
create_task()
    ↓
Task
    ↓
Event Loop

This is why:

task_a = asyncio.create_task(a())
task_b = asyncio.create_task(b())

await task_a

allows B to run while A is waiting.

"await task_a" means:

«The current coroutine ("main") waits for Task A.»

It doesn't mean the event loop cannot execute Task B.

---

Future

A Future represents a result that will become available later.

Conceptually:

Future
  ↓
incomplete
  ↓
result becomes available
  ↓
complete

Mental model:

«Coroutine = async work
Task = scheduled coroutine
Future = placeholder for a future result»

---

4.7 "gather()", "wait()", "as_completed()"

"asyncio.gather()"

Run multiple awaitables concurrently and collect their results.

results = await asyncio.gather(
    a(),
    b(),
    c()
)

If:

A → 3s
B → 1s
C → 2s

completion order:

B → C → A

but:

results

is:

["A", "B", "C"]

because "gather()" preserves input order.

Result type

type(results)
# list

Exceptions

Default:

await asyncio.gather(a(), b(), c())

If one raises, the exception is propagated to the caller.

Other operations are not automatically cancelled simply because one raised.

"return_exceptions=True"

results = await asyncio.gather(
    a(),
    b(),
    c(),
    return_exceptions=True
)

Possible result:

[
    "A",
    ValueError("B failed"),
    "C"
]

Useful when individual failures can be handled independently.

---

"asyncio.as_completed()"

Processes results in completion order.

Conceptually:

for future in asyncio.as_completed(tasks):
    result = await future

If:

B → 1s
C → 2s
A → 3s

you process:

B → C → A

Use when you want to process results as soon as they arrive.

---

"asyncio.wait()"

Returns:

done, pending = await asyncio.wait(tasks)

You get Task objects rather than a result list.

Useful modes

return_when=asyncio.FIRST_COMPLETED

Returns when any task finishes.

Important:

«"FIRST_COMPLETED" means first task to complete, not necessarily first successful task.»

The first completed task could have raised an exception.

Racing services

For:

Service A → 5s
Service B → 1s
Service C → 4s

you can use:

done, pending = await asyncio.wait(
    tasks,
    return_when=asyncio.FIRST_COMPLETED
)

Then potentially cancel remaining tasks:

for task in pending:
    task.cancel()

---

Comparison

| "gather()"| "as_completed()"| "wait()"
Main purpose| Collect all results| Process as they finish| Inspect task state
Result order| Input order| Completion order| Task objects
Early processing| No| Yes| Yes
"FIRST_COMPLETED"| No| Natural completion processing| Yes
Returns| List| Completion iterator| "(done, pending)"

---

4.8 Timeouts & Cancellation

Timeouts prevent slow operations from consuming resources indefinitely.

"wait_for()"

result = await asyncio.wait_for(
    call_api(),
    timeout=3
)

If it doesn't finish within 3 seconds, "TimeoutError" is raised.

Important cancellation chain

Timeout
   ↓
wait_for() cancels underlying operation
   ↓
operation receives CancelledError
   ↓
operation performs cleanup and re-raises
   ↓
wait_for() raises TimeoutError to caller

Example:

async def call_api():
    try:
        await asyncio.sleep(10)
    except asyncio.CancelledError:
        print("API cancelled")
        raise

try:
    await asyncio.wait_for(
        call_api(),
        timeout=2
    )
except asyncio.TimeoutError:
    print("Timeout")

Output:

API cancelled
Timeout

Important distinction

"CancelledError"

- Someone/something requested that the operation stop.

"TimeoutError"

- The allowed deadline was exceeded.

"wait_for()" handles the cancellation caused by its own timeout and reports the timeout to its caller.

---

Explicit cancellation

task = asyncio.create_task(work())

task.cancel()

The coroutine can handle cancellation:

try:
    await work()
except asyncio.CancelledError:
    cleanup()
    raise

Generally, don't silently swallow "CancelledError".

---

"asyncio.timeout()"

Modern Python also supports:

async with asyncio.timeout(3):
    result = await call_api()

Useful for applying a timeout to a block/scope.

---

Timeout + gather

results = await asyncio.wait_for(
    asyncio.gather(
        call_db(),
        call_vector_db(),
        call_mcp()
    ),
    timeout=5
)

This establishes an overall deadline for the concurrent operation.

Production principle

Timeouts should often propagate through the system.

Don't let:

Client gives up
       ↓
API request ends
       ↓
MCP continues running for 60s

if that work is no longer useful.

---

4.9 Async Synchronization

"asyncio.Lock"

Protects shared state from concurrent coroutine access.

Example race:

counter = 0

async def increment():
    global counter

    current = counter
    await asyncio.sleep(0)
    counter = current + 1

Two coroutines can both read "0" before either writes, resulting in:

counter = 1

instead of "2".

Fix

lock = asyncio.Lock()

async def increment():
    global counter

    async with lock:
        current = counter
        await asyncio.sleep(0)
        counter = current + 1

Only one task enters the critical section at a time.

Critical section

async with lock:
    ...

Keep it small.

Avoid unnecessarily holding a lock across slow I/O:

# Usually bad
async with lock:
    await external_api()
    update_state()

Prefer:

result = await external_api()

async with lock:
    update_state(result)

if the API call doesn't need protection.

---

"asyncio.Semaphore"

Controls the maximum number of concurrent operations.

sem = asyncio.Semaphore(3)

Then:

async with sem:
    await call_api()

At most 3 tasks can be inside simultaneously.

For 10 calls, capacity 3, each taking 2 seconds:

Batch-like execution:

3 → 2s
3 → 2s
3 → 2s
1 → 2s

Total ≈ 8s

General approximation for equal-duration work:

ceil(N / concurrency_limit) × task_duration

Lock vs Semaphore

Lock
  → capacity 1
  → protect shared state

Semaphore(N)
  → capacity N
  → control concurrency

Typical use cases for Semaphore:

- external API calls
- MCP calls
- LLM calls
- vector DB queries
- DB operations
- connection/resource limits

---

"asyncio.Event"

An Event is a shared signal/flag.

event = asyncio.Event()

Initially:

event.is_set() == False

Wait:

await event.wait()

Signal:

event.set()

Example

Model loading:

model_ready = asyncio.Event()

# Request handler
await model_ready.wait()

When model finishes loading:

model_ready.set()

All currently waiting tasks can proceed.

Future:

await model_ready.wait()

also returns immediately while the event remains set.

Reset:

model_ready.clear()

After clearing, future "wait()" calls block again.

Event mental model

OFF
 ↓
wait() → blocked

set()
 ↓
ON
 ↓
waiting tasks wake
 ↓
future wait() → immediate

clear()
 ↓
OFF

---

"asyncio.Condition"

A Condition is useful when tasks need to coordinate around shared state.

Mental model:

Condition
   =
Lock + waiting/notification mechanism

Producer-consumer example

queue = []
condition = asyncio.Condition()

Consumer:

async with condition:
    while not queue:
        await condition.wait()

    item = queue.pop(0)

Producer:

async with condition:
    queue.append(job)
    condition.notify()

What happens?

Consumer:

queue empty
    ↓
condition.wait()
    ↓
WAITING

Producer adds a job:

queue.append(job)
    ↓
condition.notify()

Consumer becomes runnable.

When scheduled, it resumes from the "await":

await condition.wait()
# continues here

Then it checks:

while not queue:

again.

Why "while", not "if"?

Because notification means:

«Something changed; check the condition again.»

It does not guarantee that the desired state is still true.

Pattern:

async with condition:
    while not condition_is_true:
        await condition.wait()

    # condition is true
    do_work()

Event vs Condition

Event:

«"Wait until this signal/state flag is set."»

Example:

Wait until model is ready.

Condition:

«"Wait until a particular shared-state condition becomes true."»

Example:

Wait until job queue is non-empty.

Condition lifecycle

condition.wait()
       ↓
release lock + wait
       ↓
notify()
       ↓
become runnable
       ↓
event loop schedules coroutine
       ↓
re-acquire lock
       ↓
re-check condition
       ↓
continue OR wait again

High-Value Interview Traps

1. Does "await" automatically mean concurrency?

No.

await a()
await b()

is sequential.

Use tasks/gather for concurrent independent operations.

---

2. Does asyncio mean parallelism?

No.

Asyncio primarily provides concurrent I/O.

CPU-heavy Python code still blocks the event-loop thread unless moved elsewhere.

---

3. Does the GIL make threading useless?

No.

Threads are useful for blocking I/O.

The GIL primarily limits CPU-bound pure-Python execution within the same interpreter.

---

4. Does one event-loop thread mean no race conditions?

No.

Coroutines can interleave at "await" points.

Use "asyncio.Lock" when shared state needs protection.

---

5. Does "create_task()" execute the coroutine immediately?

It schedules the coroutine as a Task; the event loop executes it when it gets a chance.

---

6. Does "gather()" return results in completion order?

No.

It preserves input order.

Completion: B → C → A

gather result:
[A, B, C]

---

7. Does "FIRST_COMPLETED" mean first successful result?

No.

It means the first Task to finish, including one that finishes with an exception.

---

8. Does "wait_for()" simply stop waiting?

No.

When its timeout expires, it cancels the underlying operation and reports the timeout to its caller.

---

9. Lock vs Semaphore

Lock       → one task
Semaphore  → N tasks

---

10. Event vs Condition

Event
→ signal/flag

Condition
→ coordinate around shared state

---
